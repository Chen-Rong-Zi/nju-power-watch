# 限流对抗策略 v2 — 单批次模式 C

## 问题

每日电费查询工作流触发 epay 服务器限流（额度约 28 次/会话/60 分钟）。之前的方案（3 并发 + 0.3s 间隔）突发速率 10 req/s，在几秒内耗尽配额。

## 方案

**模式 C：1 并发 + 0.5s 请求间隔 + 无批间隔**

- 每个请求：HTTP 往返 ~0.5s + 请求延迟 0.5s = 1s
- 速率：**1 req/s**（无突发，匀速发送）
- 触发限流阈值（10 req/s）的 **10%**，安全边际大
- 17,349 间 × 1s = ~289 分钟，在 360 分钟超时内

## 架构

```
                    config/room_ids.json (17,349 rooms)
                              │
                    一次查询全部房间，不切分
                              │
                    1 并发 → 0.5s 请求间隔
                    100 间/子批次（用于进度显示和重试粒度）
                              │
                    子批次触发限流 → 60 分钟后只重试限流房间
                              │
                    单次查询完成 → 生成聚合 → 提交
```

## 参数

| 参数 | 值 | 说明 |
|------|------|------|
| 并发数 | 1 | 单线程，无突发 |
| 请求间隔 | 0.5s | 1 req/s 匀速 |
| 子批次大小 | 100 | 仅用于进度显示和重试粒度 |
| 批间隔 | 无 | 不需要冷却期 |
| 工作流超时 | 360min | GitHub Actions 硬上限 |
| 限流重试 | 最多 2 次，每次 60 分钟 | 只重试被限流的房间 |

## 耗时估算

```
17,349 间 × 1s = 289 分钟（请求耗时）
+ 0 分钟（批间隔）
= 289 分钟 ≤ 360 分钟 ✓
```
